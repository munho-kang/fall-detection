낙상 감지 시스템 — 백엔드 구현 설명

Java 21 · Spring Boot 4.1.0 · PostgreSQL 18 — backend/가 어떻게 만들어졌고 어떻게 동작하는가.

2026-07-26 기준. Spring의 기본 개념(어노테이션·의존성 주입·JPA)은 안다고 전제하고, 이 프로젝트가 왜 그렇게 했는지에 지면을 쓴다.

1전체 지도 — 무엇으로 만들어졌나

이 백엔드가 하는 일은 한 줄로 요약된다. 브라우저가 판정한 낙상을 받아 저장하고, 보호자에게 알리고, 보호자만 볼 수 있게 돌려준다. 영상도 관절 좌표도 서버에 오지 않는다 — 낙상이 확정된 순간 4개 필드만 한 번 도착한다.

원래 Django + DRF로 만들어져 있었고 2026-07-25에 Spring Boot로 전면 교체됐다. 이때 클라이언트(웹·Flutter 앱)를 한 줄도 고치지 않는 것이 최우선 제약이었다. 이 문서에 반복해서 나오는 "기존 계약"이라는 말은 전부 이 제약을 가리킨다. 경로의 끝 슬래시, 상태 코드, snake_case 필드명, 에러 JSON의 모양까지 전부 Django 시절 그대로여야 했다.

요청이 지나는 계층

filter 토큰을 확인하고 "누구인가"를 확정한다. 실패해도 여기서 응답하지 않는다.
↓
controller HTTP만 안다. 상태 코드를 고르고 DTO로 변환한다. 로직은 없다.
↓
service 규칙이 사는 곳. 소유권·멱등성·검증이 전부 여기 있다.
↓
repository 메서드 이름이 곧 쿼리다. 구현체를 쓰지 않는다.
↓
domain 테이블에 대응하는 엔티티. 상태를 바꾸는 메서드를 스스로 갖는다.

계층 규칙은 하나다. 컨트롤러는 얇게, 서비스는 두껍게. FallController 전체가 46줄이고 그중 로직이라 부를 만한 것은 "생성됐으면 201과 푸시, 아니면 200"이라는 한 줄뿐이다. 나머지 판단은 전부 FallService에 있다.

데이터 모델 — 엔티티 6개

전부 guardian(보호자 계정)에 매달려 있다. 계정을 지우면 그 계정의 데이터가 ON DELETE CASCADE로 전부 따라 지워진다.

엔티티역할핵심 제약
Guardian 보호자 계정. Django의 User를 대체하며 username·password만 쓴다. username 유니크

보호자가 "안방 1"을 삭제해도 과거 낙상 기록은 그대로 남아야 한다. FK로 묶으면 방 삭제가 기록을 깨거나(CASCADE) 방 삭제 자체를 막는다(RESTRICT). 낙상 기록은 "그때 그 방에서 일어난 일"이라는 사실이고, 방 테이블의 현재 상태와는 별개다. 그래서 FallEvent는 room_name·room_number를 사건 발생 시점의 스냅샷으로 저장한다.

2요청 한 건의 여정 — POST /api/falls/

이 절 하나로 백엔드 전체의 골격이 잡힌다. 가장 중요한 요청 하나가 도착해서 응답이 나갈 때까지를 끝까지 따라간다. 나머지 절은 여기서 스쳐 지나간 것들을 하나씩 파고드는 것이다.

감지 브라우저가 낙상을 확정하면 이 요청 하나를 보낸다.

curl -X POST http://127.0.0.1:8000/api/falls/ \
  -H "Authorization: Token 9f3c1a…(40자)" \
  -H "Content-Type: application/json" \
  -d '{
        "room_name":   "안방",
        "room_number": 1,
        "occurred_at": "2026-07-26T14:30:00+09:00",
        "confidence":  0.94
      }'

토큰 필터가 "누구인가"를 확정한다 config/TokenAuthFilter.java:29

Spring Security의 필터체인이 먼저 요청을 받는다. 커스텀 필터가 Authorization 헤더를 읽어 auth_token 테이블과 대조한다.

String header = request.getHeader("Authorization");
if (header != null && header.startsWith(PREFIX)) {      // PREFIX = "Token "
    String key = header.substring(PREFIX.length()).trim();
    // 키가 틀리면 컨텍스트를 비워둔 채 통과 — 뒤의 인가 단계가 401 엔트리포인트로 보낸다
    authTokenRepository.findById(key).ifPresent(token ->
        SecurityContextHolder.getContext().setAuthentication(
            new UsernamePasswordAuthenticationToken(token.getGuardian(), null, List.of())));
}
chain.doFilter(request, response);

AuthToken의 PK가 키 문자열이라서 findById(key) 한 번이 곧 토큰 대조다. 별도 조회 메서드가 필요 없다.

여기서 401을 던지지 않는 것이 요점이다. 자세한 이유는 3절에 있다.

인가 단계가 통과 여부를 결정한다 config/SecurityConfig.java:34

/api/falls/는 permitAll 목록에 없으므로 authenticated()가 적용된다. 앞 단계에서 SecurityContext가 채워졌으면 통과하고, 비어 있으면 여기서 401 JSON이 나가고 요청은 끝난다.

컨트롤러가 인증 주체와 본문을 받는다 controller/FallController.java:37

@PostMapping("/api/falls/")
public ResponseEntity<FallEventResponse> create(@AuthenticationPrincipal Guardian guardian,
                                                @Valid @RequestBody FallEventRequest request) {

@AuthenticationPrincipal Guardian이 1단계에서 넣어둔 Guardian 엔티티를 그대로 꺼내 준다. 클라이언트가 보낸 값이 아니라 토큰에서 유도된 값이라는 점이 4절의 출발점이다.

@Valid가 붙어 있으므로 이 메서드 본문이 실행되기 전에 DTO의 제약(@NotBlank·@Size·@Min…)이 검사된다. 하나라도 어기면 예외가 던져져 6절의 핸들러가 400을 만든다.

서비스가 "이미 있는 낙상인가"를 먼저 묻는다 service/FallService.java:33

public CreateResult create(Guardian guardian, FallEventRequest request) {
    Instant occurredAt = request.occurredAt().toInstant();   // +09:00 입력 → UTC 저장

    Optional<FallEvent> existing = findDuplicate(guardian, request, occurredAt);
    if (existing.isPresent()) {
        return new CreateResult(existing.get(), false);   // 재전송 — 기존 행, 푸시 없음
    }
    try {
        FallEvent saved = fallEventRepository.saveAndFlush(new FallEvent(
            guardian, request.roomName(), request.roomNumber(), occurredAt,
            request.confidence()));
        return new CreateResult(saved, true);
    } catch (DataIntegrityViolationException e) {
        // 생성 경합 — uniq_fall_dedup에 걸렸으면 재조회해 200 경로로
        return new CreateResult(findDuplicate(guardian, request, occurredAt).orElseThrow(), false);
    }
}

반환 타입이 엔티티가 아니라 CreateResult(event, created)인 이유가 있다. 컨트롤러가 201과 200을 갈라야 하는데, 저장된 엔티티만 봐서는 그게 방금 만든 것인지 원래 있던 것인지 알 수 없다. 그래서 서비스가 "새로 만들었다"는 사실을 함께 돌려준다.

왜 save가 아니라 saveAndFlush인지, 왜 try/catch가 필요한지는 5절에서 다룬다.

컨트롤러가 상태 코드를 고르고 푸시를 건다 controller/FallController.java:40

FallService.CreateResult result = fallService.create(guardian, request);
if (result.created()) {
    pushService.sendToGuardianAsync(result.event());   // 201일 때만 발송
}
return ResponseEntity.status(result.created() ? HttpStatus.CREATED : HttpStatus.OK)
    .body(FallEventResponse.from(result.event()));

컨트롤러의 로직은 이게 전부다. 푸시가 created() 안쪽에 있는 것이 중요하다 — 감지 브라우저가 오프라인 큐에 쌓아둔 낙상을 재전송해도 보호자 폰이 다시 울리지 않는다.

응답은 즉시 나가고, 푸시는 다른 스레드에서 진행된다 service/PushService.java:36

sendToGuardianAsync에는 @Async("pushExecutor")가 붙어 있다. 호출은 즉시 반환되고 실제 발송은 전용 스레드풀에서 일어난다. 브라우저 벤더의 푸시 서버가 응답할 때까지 기다리느라 낙상 등록 응답이 늦어지면 안 되기 때문이다.

HTTP/1.1 201 Created

{
  "id": 42,
  "room_name": "안방",
  "room_number": 1,
  "occurred_at": "2026-07-26T05:30:00Z",     // +09:00이 UTC로 변환됐다

occurred_at과 created_at은 다른 시각이다.

occurred_at은 브라우저가 판정한 낙상 순간이고, created_at은 서버에 도착해 저장된 시각이다. 평소엔 1초 차이지만, 감지 기기가 오프라인이었다가 나중에 재전송하면 몇 시간 벌어질 수 있다. 보호자에게는 occurred_at을 보여줘야 한다 — 알림이 늦게 왔다고 넘어진 시각까지 늦어지는 것은 아니기 때문이다.

이제 이 여정에서 스쳐 간 것들을 하나씩 본다. 누구인지 확정하는 방법(3절), 남의 데이터를 막는 방법(4절), 중복을 흡수하는 방법(5절), 에러를 만드는 방법(6절), 푸시를 보내는 방법(7절)이다.

3인증 — 토큰 하나로 끝내기

로그인하면 40자 hex 문자열 하나를 받고, 이후 모든 요청에 그것을 헤더로 붙인다. 그게 전부다.

Authorization: Token 9f3c1a4b8e2d7c6f5a0b1e3d9c8a7f6b5e4d3c2a

왜 JWT가 아닌가

이 토큰은 DB에 저장되는 불투명 토큰이다. JWT처럼 자체적으로 정보를 담지 않고, 그냥 auth_token 테이블의 PK다.

성질이 프로젝트의 DB 토큰JWT였다면
검증DB 조회 1회서명 검증만, DB 불필요
만료없다보통 짧게 두고 리프레시 토큰 병행
즉시 무효화행을 지우면 끝어렵다 — 블랙리스트가 필요
보호자당 개수1개 (유니크 제약)발급할 때마다 새로 생김

선택의 근거는 제품 요구였다. 보호자는 "한 번 로그인하면 계속 로그인된 상태"여야 한다 — 새벽에 낙상 알림을 받았는데 토큰이 만료돼 다시 로그인해야 한다면 그건 실패다. 만료 없는 DB 토큰이 이 요구를 가장 단순하게 만족시킨다. 그리고 이 프로젝트는 같은 와이파이 안에서만 도는 과제 제출용이라 JWT가 해결하는 문제(무상태 확장, 여러 서버 간 검증 공유)가 애초에 없다.

재로그인해도 같은 키가 나온다. Django DRF의 Token.objects.get_or_create를 그대로 옮긴 것이다.

service/AuthService.java:112

// DRF Token.objects.get_or_create 등가 — 재로그인해도 같은 키를 돌려준다
private String tokenFor(Guardian guardian) {
    return authTokenRepository.findByGuardianId(guardian.getId())
        .orElseGet(() -> authTokenRepository.save(new AuthToken(AuthToken.newKey(), guardian)))
        .getKey();
}

키 자체는 SecureRandom으로 만든 20바이트를 hex 40자로 편 것이다(domain/AuthToken.java:38). 예측 불가능해야 하므로 Random이 아니라 SecureRandom이어야 한다.

필터가 401을 직접 던지지 않는 이유

        // permitAll은 이 셋뿐 — 나머지는 전부 인증 필수
        .requestMatchers("/", "/api/auth/login/", "/api/auth/signup/").permitAll()
        .anyRequest().authenticated())
    .exceptionHandling(e -> e.authenticationEntryPoint(SecurityConfig::unauthorized))
    .addFilterBefore(new TokenAuthFilter(authTokenRepository),
        UsernamePasswordAuthenticationFilter.class);

anyRequest().authenticated()가 마지막에 있는 게 핵심이다. 기본값이 "잠김"이고 열어줄 곳만 명시하는 구조라, 나중에 엔드포인트를 추가할 때 인증을 깜빡해도 안전한 쪽으로 실패한다. 반대로 짰다면(기본 열림 + 잠글 곳 명시) 실수가 곧 데이터 유출이 된다.

나머지 설정도 전부 "토큰 인증"이라는 한 가지 선택에서 따라 나온다.

  • STATELESS — 세션을 아예 만들지 않는다. 매 요청이 토큰만으로 자립한다.
  • CSRF 비활성 — CSRF 공격은 브라우저가 쿠키를 자동으로 붙여주기 때문에 성립한다. 이 API는 쿠키를 안 쓰고 JS가 명시적으로 헤더를 붙여야 하므로 공격 자체가 성립하지 않는다.
  • httpBasic·formLogin 비활성 — Boot 기본값으로 켜지는 인증 방식들이다. 안 쓰면 꺼서 진입점을 줄인다.
CORS를 전 오리진 허용해도 되는 이유.

CorsConfig는 addAllowedOriginPattern("*")로 모든 오리진을 연다. 보통은 위험한 설정이지만 여기선 그렇지 않다 — 인증 정보가 쿠키가 아니라 헤더에 있기 때문이다. 다른 사이트의 JS가 이 API를 호출해도 사용자의 토큰을 알 방법이 없으므로 남의 데이터에 접근할 수 없다. 반대로 쿠키 인증이었다면 브라우저가 자동으로 자격 증명을 붙여줘서 그대로 뚫린다.

그리고 이 설정이 필요한 실제 사정이 있다. 감지 페이지는 :5500에서 뜨고, 같은 와이파이의 폰은 http://<Mac IP>:5500으로 붙는다. IP가 매번 달라져 오리진을 미리 특정할 수 없다.

비밀번호

BCryptPasswordEncoder로 해시해서 저장한다(SecurityConfig.java:52). BCrypt는 느리게 설계된 해시라 무차별 대입에 강하고, 솔트를 해시 문자열 안에 함께 담아서 별도 컬럼이 필요 없다.

가입 검증은 Django의 기본 규칙을 그대로 옮겼다(AuthService.java:64). 여기서 눈여겨볼 것은 에러를 즉시 던지지 않고 전부 모은다는 점이다.

4소유권 격리 — 왜 전부 404인가

이 백엔드는 여러 보호자 계정을 담는다. 그러니 남의 낙상 기록이 새어나가지 않는 것이 가장 중요한 안전장치다. 방법은 세 겹이다.

(a) 소유자는 요청에서 받지 않고 토큰에서 유도한다

FallEventRequest에는 guardian 필드가 아예 없다. 클라이언트가 {"guardian": 7}을 보내도 DTO에 담길 자리가 없다.

dto/FallEventRequest.java

(b) 조회에 항상 소유자 조건을 함께 건다

리포지토리 메서드 이름을 보면 규칙이 한눈에 보인다. ById로 끝나는 메서드가 없다.

Spring Data JPA는 이 메서드 이름을 파싱해서 쿼리를 만든다. 구현 코드를 쓰지 않으므로 "WHERE 절에 guardian을 빼먹는" 실수 자체가 일어나기 어렵다.

(c) 남의 것은 403이 아니라 404다

service/FallService.java:51

여기가 초보자가 놓치기 쉬운 지점이다. "권한이 없다"는 뜻이면 403 Forbidden이 맞아 보인다. 그런데 403은 그 자체로 정보를 흘린다.

403과 404가 흘리는 정보의 차이.

공격자가 /api/falls/1/acknowledge/부터 순서대로 찔러본다고 하자.

  • 403을 주면 — "이 id는 존재하지만 네 것이 아니다"라는 뜻이 된다. 403이 오는 id를 세면 서버에 낙상 기록이 몇 건 있는지 알 수 있고, 404와 403의 경계로 다른 계정의 활동 시점까지 추정된다.
  • 404를 주면 — 없는 것과 남의 것이 구별되지 않는다. 아무것도 알아낼 수 없다.

이것을 열거 공격 방어라고 한다. 데이터 자체는 어느 쪽이든 안 나가지만, "존재한다"는 사실도 정보라는 관점이다.

이 패턴이 서비스 전체에 일관되게 적용돼 있다. RoomService.get도 같은 모양이고(RoomService.java:34), 방 수정·삭제는 전부 이 get을 먼저 통과하므로 자동으로 같은 보호를 받는다.

5멱등성 — 같은 낙상은 두 번 저장되지 않는다

이 절이 이 백엔드에서 가장 흥미로운 부분이다. 문제는 서버가 아니라 감지 브라우저 쪽 사정에서 시작한다.

감지 페이지는 낙상을 확정하면 즉시 POST를 보낸다. 그런데 그 순간 와이파이가 끊겨 있으면 어떻게 하나. 알림을 포기할 수는 없으니 localStorage 큐에 넣어두고, 온라인이 되면 재전송한다. 문제는 "응답을 못 받았을 뿐 서버에는 저장됐을 수도 있다"는 것이다.

그래서 재전송은 반드시 일어나야 하고, 중복 저장은 반드시 막혀야 한다.

같은 낙상을 정의한다

중복을 막으려면 먼저 "같은 낙상"이 뭔지 정해야 한다. 이 프로젝트의 답은 DB 제약에 박혀 있다.

resources/db/migration/V1__init.sql:27

-- 오프라인 큐 재전송 멱등성의 근거 — 같은 낙상은 두 행이 될 수 없다
CONSTRAINT uniq_fall_dedup UNIQUE (guardian_id, room_name, room_number, occurred_at)

누가 · 어느 방에서 · 언제 넘어졌는지가 같으면 같은 낙상이다. occurred_at은 브라우저가 판정한 시각이라 재전송해도 값이 변하지 않는다 — 그래서 열쇠로 쓸 수 있다. 만약 서버 도착 시각(created_at)을 썼다면 재전송마다 값이 달라져 중복 판정이 불가능했을 것이다.

왜 애플리케이션 코드가 아니라 DB 제약인가.

"저장 전에 조회해서 있으면 건너뛴다"만으로는 동시에 두 요청이 오면 뚫린다. 둘 다 조회에서 "없음"을 보고 둘 다 저장하는 경합이 생긴다. DB 유니크 제약은 이걸 원천적으로 막는다 — 어느 쪽이 이기든 하나는 반드시 실패한다. 애플리케이션 검사는 최적화이고, 제약이 진짜 방어선이다.

3단 방어 구조

2절에서 본 FallService.create를 다시 보면 세 단계가 겹쳐 있다.

단계담당
1findDuplicate로 먼저 조회흔한 경우를 빠르게 처리 (재전송 대부분)
2saveAndFlush로 즉시 저장DB 제약이 최종 판정
3catch 후 재조회1과 2 사이의 경합을 흡수

왜 save가 아니라 saveAndFlush인가

JPA의 save()는 SQL을 즉시 보내지 않는다. 영속성 컨텍스트에 올려두고 트랜잭션이 끝날 때 몰아서 보낸다. 그러면 제약 위반 예외도 그때 터진다 — 이미 컨트롤러를 빠져나간 뒤다. 그 시점엔 try/catch로 잡을 수도, 200으로 바꿔 응답할 수도 없다.

saveAndFlush()는 그 자리에서 INSERT를 보낸다. 그래서 제약 위반이 이 줄에서 터지고, 바로 아래 catch가 잡아 200 경로로 돌릴 수 있다.

클래스에 @Transactional을 일부러 안 붙였다

FallService 맨 위 주석이 이렇게 시작한다.

service/FallService.java:2

// 클래스 @Transactional을 쓰지 않는다: 제약 위반 후 재조회가 새 트랜잭션이어야 하기 때문

보통 서비스 클래스에는 @Transactional을 붙이는 게 관행이다. 여기서 그렇게 하면 3단계가 동작하지 않는다.

PostgreSQL은 실패한 트랜잭션을 되살려주지 않는다.

트랜잭션 안에서 제약 위반이 나면 그 트랜잭션은 중단(aborted) 상태가 되고, 이후 모든 쿼리가 current transaction is aborted, commands ignored until end of transaction block으로 거부된다. 예외를 잡아도 소용없다 — 트랜잭션 자체가 죽어 있다.

즉 클래스에 @Transactional이 있었다면 catch 안의 findDuplicate 재조회가 반드시 실패한다. 트랜잭션 경계를 각 리포지토리 호출 단위로 두어(Spring Data의 기본 동작), 실패한 INSERT와 이어지는 SELECT가 서로 다른 트랜잭션이 되게 한 것이다.

이것은 Django가 기본으로 하던 autocommit 동작을 의도적으로 재현한 것이다. 관행을 따르지 않은 자리에는 이렇게 이유가 있고, 그래서 파일 맨 위에 주석으로 남아 있다.

acknowledge도 멱등이다

보호자가 알림 확인을 두 번 눌러도 첫 확인 시각이 유지돼야 한다.

domain/FallEvent.java:64

// 첫 확인 시각을 보존한다 — 두 번째 호출부터는 무시 (멱등)
public void acknowledgeNow() {

        acknowledgedAt = Instant.now().truncatedTo(ChronoUnit.MICROS);

판단이 서비스가 아니라 엔티티 안에 있다. "확인 시각은 한 번만 찍힌다"는 것은 이 데이터의 성질이지 특정 서비스의 사정이 아니므로, 데이터를 가진 쪽이 스스로 지키게 한 것이다.

마이크로초로 자르는 이유.

Instant.now()는 나노초까지 담을 수 있지만 PostgreSQL timestamptz는 마이크로초까지만 저장한다. 자르지 않으면 응답에 실린 값(메모리)과 나중에 DB에서 다시 읽은 값이 미세하게 달라진다. 저장 가능한 정밀도로 미리 맞춰 두 값이 항상 같게 만든 것이다.

이 멱등성이 막지 못하는 것도 있다.

열쇠에 occurred_at이 들어 있으므로, 감지 로직이 같은 낙상을 다른 시각으로 두 번 판정하면 서버는 다른 낙상으로 본다. 실제로 그런 버그가 있었다 — 알림 후 사람이 가구에 가려졌다가 누운 채 재검출되면 상태 기계가 잘못 재무장돼 두 번째 전송이 나갔다. 서버에서는 흡수할 방법이 없어 감지 쪽(web/js/detector.js)을 고쳤다. 멱등성은 열쇠가 안정적일 때만 성립한다.

6검증과 에러 계약 — 형태가 요구사항이다

에러 응답의 모양이 이 백엔드에서는 요구사항이다. 클라이언트를 한 줄도 못 고치는 제약이 있었으므로, 웹과 앱이 이미 파싱하고 있는 Django REST Framework의 형태를 그대로 재현해야 했다.

    if (!errors.isEmpty()) throw new FieldValidationException(errors);
}

그래서 RoomRequest의 필드는 String name, Integer number로 둘 다 nullable이고 어노테이션이 하나도 없다. "안 보낸 것"과 "빈 값을 보낸 것"을 구분해야 하기 때문이다 — int였다면 안 보낸 필드가 0으로 채워져 둘을 구분할 수 없다.

예외 하나로 모아서 응답으로 바꾼다

검증이 어디서 실패하든 결국 같은 형태의 JSON이 나가야 한다. 그 변환을 한 곳에 모은 것이 GlobalExceptionHandler다.

예외발생 지점응답
FieldValidationException서비스 수동 검증400 + 담긴 맵 그대로
MethodArgumentNotValidException@Valid 실패 (Spring이 던짐)400 + 필드명 snake_case 변환 후 그룹핑
NotFoundException소유권 조회 실패404 {"detail": "찾을 수 없습니다."}
HttpMessageNotReadableException본문이 JSON이 아님400 {"detail": "요청 본문을…"}
(인증 없음)Security 인가 단계401 — 필터체인이 처리, 여기 안 온다

@RestControllerAdvice가 붙어 있어 모든 컨트롤러에 자동 적용된다. 덕분에 컨트롤러에 try/catch가 한 줄도 없다.

snake_case 변환이 필요한 이유는 이름이 두 번 바뀌기 때문이다. JSON의 room_name은 @JsonProperty로 자바 필드 roomName에 매핑되는데, 검증 실패 시 Spring이 알려주는 필드명은 자바 쪽 이름인 roomName이다. 클라이언트는 room_name으로 에러를 찾으므로 되돌려줘야 한다.

error/GlobalExceptionHandler.java:33

for (FieldError fe : ex.getBindingResult().getFieldErrors()) {
    errors.computeIfAbsent(snakeCase(fe.getField()), k -> new ArrayList<>())
        .add(fe.getDefaultMessage());
}

한 필드에 여러 위반이 걸릴 수 있으므로 computeIfAbsent로 배열에 모은다. DRF의 형태가 값이 아니라 배열인 이유도 같다.

고정 문자열 두 개는 함부로 못 바꾼다.

대부분의 에러 문구는 클라이언트가 그대로 표시만 하므로 자유롭게 바꿔도 된다. 그런데 두 개는 클라이언트가 문자열을 비교해서 분기한다.

  • "같은 이름과 번호의 방이 이미 있습니다." — 그래서 RoomService.DUPLICATE_ROOM_MESSAGE 상수로 뽑혀 있다.
  • "웹 푸시가 설정되지 않았습니다." — 보호자 페이지가 이 503으로 "푸시 미설정" 안내를 띄운다.

7웹 푸시 — 실패해도 되는 기능

보호자 페이지를 닫아둬도 알림이 오게 하는 기능이다. 설계 원칙이 다른 절과 완전히 다르다. 이 기능은 실패해도 된다.

왜냐하면 안전망이 이미 있기 때문이다. 앱과 보호자 페이지는 5초마다 GET /api/falls/를 폴링한다. 푸시가 안 가도 화면을 켜 두면 알림이 뜬다. 푸시는 "화면이 꺼져 있을 때도 알려주는" 추가 편의일 뿐이다.

이 판단이 코드 전체를 관통한다.

(a) 키가 없으면 조용히 꺼진다

웹 푸시에는 VAPID 키가 필요하다. 서버 실행 시 환경변수로 주는데, 없어도 서버가 정상 기동한다.

resources/application.yml:15

push:
  vapid:
    private-key: ${VAPID_PRIVATE_KEY:}   # 미설정이면 푸시 조용히 비활성
    subject: ${VAPID_SUBJECT:}

${VAR:}의 콜론 뒤 빈 값이 기본값이다. 키가 없으면 VapidService.isConfigured()가 false가 되고, 발송 시도 자체를 건너뛴다. 기능 하나가 설정되지 않았다고 서버 전체가 안 뜨는 것은 과한 반응이라는 판단이다.

(b) 공개키는 저장하지 않고 계산한다

VAPID는 공개키·개인키 쌍인데 이 서버는 개인키만 받는다. 공개키는 필요할 때 계산한다.

service/VapidService.java:44

// P-256 공개키 = G × d (비압축 점 65바이트)를 base64url로.
public String publicKey() {
    if (!isConfigured()) return null;
    if (cachedPublicKey != null) return cachedPublicKey;
    try {
        ECNamedCurveParameterSpec spec = ECNamedCurveTable.getParameterSpec("prime256v1");
        BigInteger d = new BigInteger(1, Base64.getUrlDecoder().decode(privateKey));
        byte[] point = spec.getG().multiply(d).normalize().getEncoded(false);
        cachedPublicKey = Base64.getUrlEncoder().withoutPadding().encodeToString(point);
        return cachedPublicKey;
    } catch (Exception e) {
        log.error("VAPID 공개키 파생 실패 — 키 형식을 확인하세요…", e);
        return null;   // → 503 경로. 서버는 계속 돈다
    }
}

타원곡선 암호에서 공개키는 개인키로부터 유일하게 결정된다(기준점 G를 개인키 d배 한 점). 그래서 둘 다 보관할 이유가 없다 — 설정할 값이 절반으로 줄고, 두 키가 짝이 안 맞는 실수가 원천적으로 사라진다. 계산 결과는 캐시해서 한 번만 한다.

여기서도 실패 처리는 같다. 키 형식이 잘못돼도 null을 돌려주고 로그만 남긴다. 그러면 /api/push/vapid-key/가 503을 주고, 보호자 페이지가 "푸시 미설정" 안내를 띄운다.

(c) 발송은 응답 밖에서, 실패는 삼킨다

service/PushService.java:36

// POST 응답이 외부 HTTP를 기다리지 않도록 스레드풀에서 발송한다
@Async("pushExecutor")
public void sendToGuardianAsync(FallEvent event) { sendToGuardian(event); }

public void sendToGuardian(FallEvent event) {
    try {
        if (!vapidService.isConfigured()) return;   // 키 미설정 — 조용히 비활성
        Long guardianId = event.getGuardian().getId();
        for (PushDevice device : pushDeviceRepository.findByGuardianId(guardianId)) {
            sendOne(device, event);
        }
    } catch (Exception e) {
        log.error("푸시 발송 중 예상 밖 오류 (event={})", event.getId(), e);   // 삼킨다
    }
}

두 겹으로 감싼다. sendOne이 기기 하나의 실패를 잡아 다음 기기 발송을 막지 않게 하고, 바깥 try가 그 밖의 모든 예외를 잡아 API 응답에 영향을 주지 않게 한다. 보통은 예외를 삼키는 게 나쁜 습관이지만, 여기서는 "낙상은 저장됐는데 푸시 실패로 500을 돌려주는" 상황이 훨씬 나쁘다.

스레드풀은 데몬 스레드로 만든다(AsyncConfig.java:20). 데몬이 아니면 발송 대기 중인 작업이 남아 있을 때 서버가 종료되지 않고 매달린다.

(d) 만료된 구독은 그 자리에서 정리한다

service/PushService.java:56

int status = webPushClient.send(device.getToken(), payloadJson(event));
if (status == 404 || status == 410) {
    pushDeviceRepository.delete(device);   // 만료된 구독은 그 자리에서 정리한다
} else if (status >= 400) {
    log.error("웹 푸시 발송 실패 (device={}, status={})", device.getId(), status);
}

브라우저를 지우거나 알림을 껐으면 푸시 서비스가 404/410 Gone을 준다. 이건 일시적 실패가 아니라 영구적으로 죽은 구독이라는 뜻이므로, 재시도하지 않고 삭제한다. 별도 정리 배치가 필요 없어진다.

(e) 라이브러리를 인터페이스 뒤에 숨긴다

WebPushClient는 메서드 하나짜리 인터페이스다.

// 웹 푸시 발송 어댑터 경계 — 테스트는 이 인터페이스를 목으로 바꿔 외부 HTTP를 차단한다
public interface WebPushClient {
    int send(String subscriptionJson, String payload) throws Exception;
}

구현체 MartijnDwarsWebPushClient가 실제 라이브러리를 쓴다. 인터페이스를 하나 끼운 이유는 테스트다. 이게 없으면 푸시 테스트가 진짜 구글 서버에 요청을 보낸다 — 느리고, 네트워크가 없으면 실패하고, 결과가 매번 다르다. 테스트에서는 이 인터페이스를 가짜 구현으로 바꿔 "무엇이 발송됐는지"만 확인한다.

실제로 겪은 함정 — 인코딩을 명시해야 했다.

라이브러리의 인자 없는 send(notification)은 구식 AESGCM 인코딩으로 동작하는데, 구글의 푸시 서버가 이걸 403 crypto-key header had invalid format으로 거부한다. 구독도 키 파생도 전부 정상인데 발송만 실패해서 원인을 찾기 어려웠다. 표준 인코딩을 명시해서 해결했다.

var response = delegate().send(new Notification(subscription, payload), Encoding.AES128GCM);

라이브러리 기본값이 항상 현재 표준은 아니라는 사례다. MartijnDwarsWebPushClient.java:35에 이 경위가 주석으로 남아 있다.

구독 토큰은 왜 전역 유니크인가

PushDevice.token은 보호자별이 아니라 전체에서 유니크다. 브라우저 하나가 만드는 구독은 하나뿐이라 계정보다 기기가 더 근본적인 단위이기 때문이다.

이 제약 덕분에 계정 전환이 자연스럽게 처리된다.

service/PushDeviceService.java:20

@Transactional
public void register(Guardian guardian, String kind, String token) {
    pushDeviceRepository.findByToken(token).ifPresentOrElse(
        device -> device.reassign(guardian, kind),   // 다른 계정에 있으면 현 사용자로 이전
        () -> pushDeviceRepository.save(new PushDevice(guardian, kind, token)));
}

A 계정으로 알림을 켜뒀다가 로그아웃하고 B 계정으로 켜면, 새 행이 생기는 게 아니라 기존 행의 주인이 바뀐다. 이걸 안 했다면 A의 낙상 알림이 B가 쓰는 브라우저로 계속 갔을 것이다.

@Transactional이 붙은 이유는 reassign이 조회한 엔티티의 필드만 바꾸고 save를 호출하지 않기 때문이다. JPA는 트랜잭션이 끝날 때 관리 중인 엔티티의 변경을 감지해 자동으로 UPDATE를 보낸다(변경 감지). 트랜잭션이 없으면 이 동작이 일어나지 않아 변경이 사라진다.

8마이그레이션 · 테스트 · 실행

스키마는 Flyway가 소유한다

JPA는 엔티티를 보고 테이블을 자동 생성할 수 있다. 이 프로젝트는 그 기능을 껐다.

resources/application.yml:10

jpa:
  hibernate:
    ddl-auto: none     # 스키마는 Flyway가 소유한다
  open-in-view: false

대신 db/migration/V1__init.sql이 스키마의 유일한 정의다. 서버가 뜰 때 Flyway가 이 파일을 실행하고, 이미 적용됐으면 건너뛴다.

이유는 5절에 있다. 제약의 이름이 중요하기 때문이다. uniq_fall_dedup은 이 백엔드의 멱등성이 걸려 있는 계약인데, 자동 생성에 맡기면 Hibernate가 UK_a3f9c… 같은 이름을 무작위로 붙이고 버전에 따라 달라질 수도 있다. SQL로 직접 쓰면 이름도 형태도 결정적이다.

open-in-view: false도 짚어둘 만하다. 기본값이 true인데, 그 경우 HTTP 응답을 만드는 동안까지 DB 연결을 붙잡고 있어 지연 로딩이 아무 데서나 쿼리를 날린다. 꺼두면 지연 로딩 문제가 컨트롤러가 아니라 서비스 안에서 즉시 드러난다.

비동기 스레드에서 지연 로딩을 피한 자리.

PushService.sendToGuardian은 event.getGuardian().getId()만 부른다. getUsername()이었다면 실제 조회가 필요해 실패했을 것이다 — 비동기 스레드에는 영속성 컨텍스트가 없기 때문이다. getId()는 프록시가 이미 알고 있는 값이라 DB를 안 본다. 이 사정이 코드에 주석으로 남아 있다(PushService.java:44).

정리 — 이 백엔드에서 가져갈 것

코드는 작지만 반복해서 나타나는 판단이 몇 가지 있다.

  • 안전은 검증이 아니라 구조로 만든다. 소유자 위조를 막은 방법은 검사하는 것이 아니라 DTO에 그 필드를 두지 않는 것이었다. 리포지토리 메서드 이름에 AndGuardianId를 넣는 것도 같은 방식이다.
  • 불변식은 최대한 아래층에 둔다. 중복 방지를 애플리케이션이 아니라 DB 제약에 맡겼기 때문에 동시 요청에도 뚫리지 않는다. 애플리케이션의 사전 조회는 최적화일 뿐이다.
  • 기능마다 실패의 무게가 다르다. 낙상 저장은 실패하면 안 되지만 푸시는 실패해도 된다. 그래서 한쪽은 DB 제약까지 동원하고 다른 쪽은 예외를 삼킨다. 모든 코드에 같은 엄격함을 적용하는 것이 항상 옳지는 않다.
  • 관행을 벗어난 자리에는 이유를 남긴다. FallService에 @Transactional이 없는 것, save 대신 saveAndFlush를 쓴 것, 인코딩을 명시한 것은 전부 이유가 있고 그 이유가 주석으로 코드 옆에 있다. 다음에 읽는 사람이 "빠뜨렸나 보다" 하고 고치면 버그가 되기 때문이다.
