# 괜찮음 응답 앱 표시 설계

2026-07-27. 낙상자가 "괜찮아"라고 답해 119 신고 없이 해제된 낙상을, 보호자 앱이 "낙상자가
괜찮다고 말한 낙상 사고"로 표시하기 위한 설계다. 음성 확인·119 자동 신고 라운드
(2026-07-27-voice-check-119-design.md)의 후속이며 브레인스토밍 결정 기록이다.

## 1. 배경

음성 확인 라운드에서 "괜찮아" 응답(RESOLVED)은 감지 페이지 화면에 "응답 확인 — 신고 안 함"을
띄우고 끝난다. 서버로는 아무것도 전송되지 않아, 보호자 앱은 무서운 낙상 알림만 받고 어르신이
직접 괜찮다고 답한 사실은 모른다. 보호자가 놀라 달려가거나 전화를 거는 것 자체는 나쁘지 않지만,
시스템이 이미 아는 안심 정보를 전달하지 않는 것은 공백이다. 이 라운드는 그 정보를 앱까지
운반한다.

## 2. 범위와 결정

1. **표시 범위는 앱 알림 + 목록·상세** — 알림(로컬 알림) 문구 갱신에 더해, 알림을 지운 뒤 앱을
   열어도 알 수 있도록 목록 배지와 상세 행까지 표시한다. 보호자 웹은 이번 범위에서 제외한다
   (사용자 결정. 119의 "전 화면 표시"와 달리 안심 정보는 앱만으로 충분하다고 판단).
2. **알림은 같은 id로 교체** — 낙상 기록은 확정 5초에 만들어지고 앱 알림도 그 직후 뜨는데,
   "괜찮아"는 보통 질문(10초) 뒤 10~20초 사이에 나온다. 알림이 먼저 뜨는 게 정상 순서이므로,
   괜찮음 도착을 폴링이 관측하면 같은 알림 id로 `show`를 다시 호출해 트레이의 알림을 교체한다.
   헤드업이 한 번 더 뜨는데, 무서운 알람 뒤에 안심 정보가 갱신되는 흐름이라 자연스럽다.
   별도 후속 알림(트레이에 모순된 2건이 쌓임)과 알림 지연(낙상 알림이 20초 늦어져 안전 우선
   위배)은 제외했다.
3. **전송은 새 엔드포인트 없이 재-POST** — 119 신고(`reported_119_at`)와 같은 패턴으로, 같은
   낙상 payload에 `voice_ok_at`(응답 시각)을 붙여 `POST /api/falls/`를 한 번 더 보낸다. 서버는
   기존 행에 병합한다.
4. **조기 응답(5초 이전)은 원본 전송에 동승** — "괜찮아"가 원본 전송(5초) 전에 나오면 바로
   POST하지 않고 응답 시각만 들고 있다가 5초 원본 payload에 `voice_ok_at`을 실어 한 번에
   보낸다. 3초에 "괜찮아" 하고 4초에 일어난 낙상은 오늘 기록이 없는데, 즉시 POST하면 기록과
   푸시가 생겨 "5초 내 회복 = 없던 일" 동작이 깨지기 때문이다. 5초 전에 일어나면 원본이 안
   나가므로 괜찮음 기록도 자연히 없다.
5. **이름** — DB·API 필드는 `voice_ok_at`, 상태머신 명령은 `SEND_OK`, 앱 모델은
   `voiceOkAt`·`isVoiceOk`.

범위 밖: 보호자 웹 목록 배지, 웹 푸시 문구 변경, 119 신고의 알림 갱신(기존대로 인앱 표시만),
"괜찮아" 외 대답의 의미 해석. RESOLVED 상태 문구 등 감지 페이지 화면은 변경 없다.

## 3. 전송 경로 — 감지 페이지

- **escalation.js** — RESOLVED 전이 두 곳(조기 응답 LISTENING→RESOLVED, 질문 후
  WAITING→RESOLVED)이 `MIC_OFF`와 함께 `SEND_OK`를 내놓는다. REPORTED 경로에는 `SEND_OK`가
  없다. 상태머신은 5초 전송 시점을 모른다 — 조기 응답 처리는 배선(main.js)의 몫이다.
- **main.js** — 에피소드별 `pendingVoiceOkAt`을 둔다. `MIC_ON`(새 에피소드)에 null로 리셋하고,
  `SEND_OK`를 받으면 응답 시각을 기록한 뒤 원본 전송 여부(`lastFallPayload`)에 따라 갈린다.
  이미 나갔으면 즉시 payload에 `voice_ok_at`을 붙여 재-POST하고, 아직이면 들고 있다가 5초 원본
  payload에 동승시킨다. 재-POST 실패는 119 신고와 똑같이 기존 localStorage 큐에 실려
  재전송된다(큐 코드 변경 없음). 두 POST의 도착 순서가 뒤집혀도 서버 병합이 멱등이라 결과가
  같다.

## 4. 백엔드

`reported_119_at`과 같은 패턴이다.

- Flyway `V3__add_voice_ok_at.sql` — `fall_event`에 nullable TIMESTAMPTZ `voice_ok_at` 추가.
- `FallEvent` — `voiceOkAt` 필드와 `markVoiceOk(Instant)`. 기존 값이 null일 때만 쓰는 멱등
  병합이고 MICROS 절삭도 신고 시각과 같다.
- `FallEventRequest`·`FallEventResponse` — `voice_ok_at` 노출.
- `FallService` — 생성(201) 시 요청에 있으면 반영. 중복(200) 병합 `merge`는 현재 신고 시각
  전용인데 두 필드를 독립적으로 병합하도록 일반화한다. 쓸 것이 없으면 저장하지 않는 성질은
  유지한다.
- 푸시는 201에만 발송하는 기존 규칙 그대로 — 재-POST(200)로 인한 중복 푸시가 없다. 상태머신
  종결 상태가 하나뿐이라 같은 낙상에 `voice_ok_at`과 `reported_119_at`이 둘 다 기록되는 정상
  경로는 없지만, 서버 병합은 필드별로 독립 동작한다.

## 5. 앱

- **모델** — `voiceOkAt`(nullable DateTime)·`isVoiceOk` 추가.
- **알림 문구는 이벤트 상태에서 파생** — `isVoiceOk`면 본문 "HH:MM 발생 · 낙상자가 괜찮다고
  말한 낙상 사고입니다", 아니면 기존 "HH:MM 발생 · 확인이 필요합니다". 제목("○○방에서 낙상
  감지")과 알림 id(이벤트 id)는 유지한다 — 같은 id 재호출이 곧 교체다.
- **트래커 확장** — `NewEventTracker`가 새 이벤트(fresh)와 별개로 "이미 본 이벤트에 괜찮음이
  새로 도착"한 전이(newlyOk)를 돌려준다. 최초 호출(로그인 직후)은 기존 규칙대로 프라이밍만
  하고 둘 다 비운다 — 옛 괜찮음 이벤트로 알림 폭탄이 터지지 않는다. 처음부터 괜찮음이 실려 온
  fresh 이벤트는 fresh로만 나가고 첫 알림이 곧 괜찮음 문구라 두 번 뜨지 않는다. 목록 화면은
  fresh든 newlyOk든 같은 `Notifications.show`를 호출한다.
- **목록 trailing 우선순위** — "119 신고됨"(빨강) > "괜찮다고 말함"(초록) > 확인함/미확인.
  확인 여부는 기존대로 leading 아이콘이 계속 보여준다.
- **상세** — 상태 행 아래에 `isVoiceOk`일 때 "음성 확인 — 낙상자가 괜찮다고 말했습니다 (시각)"
  행을 추가한다. 상세는 이미 5초 재조회가 있어 보는 중에도 실시간 반영된다.

## 6. 테스트

- `web/tests/escalation.test.js` — ① 조기 응답(LISTENING→RESOLVED)에 SEND_OK 정확히 1회
  ② WAITING→RESOLVED에 1회 ③ REPORTED 경로에 0회 ④ RESOLVED 후 재무장 전까지 추가 SEND_OK
  없음.
- 백엔드 — `voice_ok_at` 신규 201 저장 / 중복 200 병합 / 이미 값 있으면 불변 / 요청에 없으면
  기존 값 유지 / 두 필드 병합 독립(한쪽만 있는 행에 다른 쪽이 도착해도 각자 병합).
- 앱 — 모델 파싱(있음·없음), 트래커(프라이밍·전이 1회·fresh+괜찮음 중복 없음·이미 안 전이
  재통지 없음), 알림 문구 파생, 목록 trailing 우선순위, 상세 행 표시.
- 알림 교체는 실기기 확인이 필요하다 — `docs/manual-verification.md`에 "괜찮아" 응답 후 앱
  알림이 괜찮음 문구로 교체되는 시연 절차를 추가한다.
