# 음성 응답 확인·119 자동 신고 설계

2026-07-27. 낙상 알림이 보호자에게 갔지만 보호자가 못 보는 경우를 위한 안전망이다. 낙상 확정 후
어르신에게 음성으로 직접 안부를 묻고, 대답이 없으면 시스템이 119 신고를 기록한다. 브레인스토밍
결정 기록이며 구현 계획의 입력이 된다.

## 1. 배경

기존 파이프라인은 낙상 확정(FALLEN) 후 5초 미회복이면 보호자에게 알림을 보내는 데서 끝난다.
보호자가 바빠서 알림을 못 보면 그 다음이 없다. 이 라운드는 그 공백을 메운다 — 감지 페이지가
어르신 방에 있다는 사실(마이크·스피커가 현장에 있다)을 이용해, 사람의 개입 없이 확인→신고까지
진행하는 에스컬레이션을 붙인다.

시연 전제는 기존과 같다. 119는 실제 발신이 아니라 **시스템에 기록되는 신고 상태**이고, 앱의 119
버튼(더미 번호)이 비활성화되며 "이미 신고됨" 문구가 나타나는 것으로 표현한다.

## 2. 범위와 결정

1. **타임라인은 낙상 확정 순간(0s) 기준** — 0s 마이크 ON, 5s 보호자 알림(기존 그대로),
   10s "괜찮으세요?" 재생, 20s 무응답이면 119 신고. 낙상 후 20초면 신고까지 끝나는 가장 빠른
   시나리오를 택했다. 보호자 알림 시점(5s)부터 다시 세는 안은 신고가 25초로 늦어져 제외.
2. **"움직이지 않음" = 못 일어남** — 기존 상태머신의 회복 판정(tilt < 45°)을 그대로 쓴다.
   누워서 버둥거려도 못 일어나면 도움이 필요한 상황이므로 질문을 미루지 않는다. 랜드마크
   이동량 기반 미세 움직임 감지는 "다쳐서 버둥거리는 사람의 신고가 계속 미뤄지는" 역효과가
   있어 제외.
3. **음성 인식은 Web Speech API** — Chrome 내장 STT(ko-KR)로 "괜찮아"를 인식한다. 인식 중
   오디오가 구글 서버로 전송되는 프라이버시 트레이드오프가 있으나, 응급 구간(낙상~해제)에만
   마이크가 켜지는 조건으로 감수한다(8절). 온디바이스 STT(Vosk, 모델 ~50MB)는 과제 범위에
   무겁고, 음량 기반 감지는 고통의 신음도 "괜찮음"으로 오인해 신고를 취소하는 치명적 결함이
   있어 제외.
4. **신고 상태는 전 화면에 표시** — 앱 상세(버튼 비활성화+문구), 앱 목록 배지, 보호자 웹 목록
   배지, 감지 페이지 진행 상태. 바쁜 보호자가 뒤늦게 목록만 봐도 "이미 신고됐구나"를 알 수
   있어야 시나리오 취지에 맞다.
5. **신고 전송은 새 엔드포인트 없이 재-POST** — 같은 낙상 payload에 `reported_119_at`을 붙여
   `POST /api/falls/`를 한 번 더 보낸다(5절).

범위 밖: 실제 119 발신, 신고 사실의 2차 푸시 알림, 질문 반복 재생, 대답의 다양한 의미 해석
("도와줘" 즉시 신고 등), 다중 인물, 보호자 응답(acknowledge)에 따른 에스컬레이션 중단.
보호자가 알림을 확인했더라도 어르신이 못 일어난 사실은 변하지 않으므로 음성 확인은 그대로
진행한다.

## 3. 타임라인

```
낙상 확정(FALLEN, 0s)                          [감지 페이지]
  마이크 ON, 청취 시작
  ├─ 5s ──▶ 보호자 알림 POST (기존 그대로)
  ├─ 10s ─▶ "괜찮으세요?" TTS 재생 (재생 중엔 청취 일시정지)
  ├─ 20s ─▶ 무응답 ──▶ 119 신고 재-POST ──▶ 앱·보호자 웹 반영
  │
  ├─ 언제든 "괜찮아" ──▶ 해제, 신고 안 함 (10s 전이면 질문도 생략)
  └─ 언제든 일어남(STANDING) ──▶ 전체 취소, 마이크 OFF
```

20s는 TTS 재생 시간과 무관한 절대 마감이다(질문이 10s에 나가고 대답 대기가 약 10초).
해제·신고·취소 후에는 일어나야만(tilt < 45°) 다음 에피소드가 재무장된다 — 기존 ALERTED
재무장과 같은 규칙이라 누워 있는 동안 중복 신고가 없다.

## 4. 감지 페이지 구조

### escalation.js — 순수 상태머신 (신규)

detector.js와 같은 스타일로 브라우저 API를 쓰지 않는다. 매 프레임 `update(detectorState, t)`를
받고, 어댑터가 주입하는 이벤트(`heardOk()`, `ttsEnded()`)로 전이하며, 한 번만 실행할 명령을
결과로 내놓는다. 가짜 타임스탬프만으로 전체 시나리오를 테스트할 수 있다.

```
IDLE ──FALLEN 진입──▶ LISTENING(0~10s) ──10s──▶ ASKING(TTS 중) ──ttsEnded──▶ WAITING(~20s) ──20s──▶ REPORTED
                          └───────────── heardOk 어디서든 ──▶ RESOLVED ──────────┘
                          └───────────── STANDING 어디서든 ──▶ IDLE(취소) ────────┘
```

- 명령: `MIC_ON`(에피소드 시작), `PLAY_QUESTION`(10s), `REPORT`(20s), `MIC_OFF`(종결·취소).
- 화면용 상태 문구도 함께 반환한다(6절).
- `NO_PERSON`은 회복이 아니다 — 넘어진 사람이 가려져도 에피소드를 유지한다. 종결은 오직
  `STANDING`(회복), `heardOk`(해제), 20s 경과(신고)뿐이다.
- `ASKING` 중 `heardOk`는 무시한다. 어댑터가 청취를 꺼두므로 원래 오지 않아야 하지만, 정지
  직전 오디오의 인식 결과가 늦게 도착할 수 있다 — 상태머신 차원에서도 버려 자기 목소리 방어를
  이중화한다. TTS 실패·스킵 시에는 바로 `WAITING`으로 넘어가 청취를 재개한다.

### speech.js — 음성 어댑터 (신규)

- **TTS** — `speechSynthesis`로 ko-KR "괜찮으세요?"를 재생하고 끝나면 `ttsEnded()`를 넣는다.
- **STT** — `webkitSpeechRecognition`(ko-KR, continuous + interim). 침묵으로 인식이 끊기면
  에피소드가 살아 있는 동안 자동 재시작한다. 인식 텍스트에 **"괜찮"이 포함되면** `heardOk()`를
  넣는다 — "괜찮아", "괜찮아요", "나 괜찮아" 모두 통과한다.
- **자기 목소리 함정** — 질문 "괜찮으세요?"에도 "괜찮"이 들어 있다. TTS 재생 동안 인식을
  켜두면 시스템이 자기 질문을 알아듣고 스스로 신고를 취소한다. TTS 시작 전에 인식을 멈추고
  끝난 뒤 재개한다.
- **마이크 권한** — 감지 시작 클릭 시 카메라와 함께 `getUserMedia({audio})`로 미리 받아 둔다.
  응급 순간에 권한 팝업이 뜨면 안 된다. 권한을 받은 직후 트랙은 바로 끄고, 실제 청취는
  에피소드 중에만 한다.
- **실패는 전부 신고 쪽으로** — STT 오류·미지원·마이크 거부는 `heardOk`가 영영 오지 않는 것,
  즉 무응답과 같다. 20s에 신고가 나간다. 확인 실패가 신고를 삼키지 않는다(안전 우선).

### main.js — 배선 (수정)

runLoop 콜백에서 `detector.update` 결과를 `escalation.update`에 넘기고, 반환된 명령을
speech.js·전송 함수·화면에 분배한다. 감지 시작 시 마이크 권한 요청을 추가한다.

## 5. 신고 전송과 백엔드

`FallEvent`에 `reported_119_at`(timestamptz, nullable) 필드를 추가한다(Flyway `V2`). 20s 시점에
감지 페이지가 **같은 낙상 payload에 `reported_119_at`(신고 시각)을 붙여 `POST /api/falls/`를
한 번 더** 보낸다.

- 서버 `create`는 요청에 `reported_119_at`이 있으면 반영한다. 신규(201)면 그대로 저장, 유니크
  키 중복(200)이면 기존 행에 병합한다. 병합은 `acknowledgeNow`와 같은 멱등 패턴 — **기존 값이
  null일 때만 쓴다.**
- 이벤트 id가 필요 없다. 5s 원본 전송이 실패해 큐에만 있던 경우에도 신고 재-POST는 독립적으로
  동작하고, 실패하면 기존 localStorage 큐에 실려 재전송된다. 큐 코드 변경은 0줄이다. 두 POST의
  도착 순서가 뒤집혀도(신고분이 먼저 201로 생성, 원본이 나중에 200 중복) 결과가 같다.
- 푸시는 201에만 발송하는 기존 규칙을 유지한다 — 정상 경로에서 재-POST는 200이라 중복 푸시가
  없다. 원본이 큐에 갇혔다가 신고분이 먼저 201이 되는 드문 경로에서는 푸시가 신고 시점에 한 번
  나가는데, 이는 결함이 아니라 지연된 첫 알림이다.
- `FallEventResponse`·앱 모델·보호자 웹에 `reported_119_at`을 노출한다.

## 6. 화면 반영

| 화면 | 변경 |
|------|------|
| 감지 페이지 | 상태 줄 추가 — "🎤 음성 확인 대기"(LISTENING) → "괜찮으세요? 확인 중"(ASKING·WAITING) → "응답 확인 — 신고 안 함"(RESOLVED) 또는 "🚨 119 자동 신고됨"(REPORTED). IDLE에서는 숨김 |
| 앱 상세 | `reported_119_at`이 있으면 119 버튼 비활성화, 문구 "응답이 없어 119에 자동 신고되었습니다". 화면이 열려 있는 동안 5초 주기로 재조회해서 보고 있는 중에 신고가 도착하면 실시간으로 잠긴다 |
| 앱 목록 | "119 신고됨" 배지 |
| 보호자 웹 목록 | 같은 배지 |

앱 상세의 재조회는 단건 GET이 없으므로 기존 목록 API를 불러 자기 id를 찾는 방식으로 한다.

## 7. 테스트

- `web/tests/escalation.test.js` (핵심) — 가짜 t로: ① 10s에 PLAY_QUESTION 1회 ② 20s에 REPORT
  정확히 1회 ③ 조기 heardOk(0~10s)면 질문 생략하고 RESOLVED ④ WAITING 중 heardOk면 RESOLVED
  ⑤ 어느 단계든 STANDING이면 취소·MIC_OFF ⑥ NO_PERSON 중 에피소드 유지 ⑦ 신고 후 재무장
  전까지 새 에피소드 없음 ⑧ ASKING 중 청취 정지(ttsEnded 전 heardOk 무시).
- 백엔드 — `reported_119_at` 포함 신규 201 저장 / 중복 200 병합 / 이미 값 있으면 불변 /
  요청에 없으면 기존 값 유지.
- 앱 — 모델 파싱, 상세 버튼 비활성화 조건.
- 보호자 웹 배지는 수동 검증으로 하고 `docs/manual-verification.md`에 절차를 추가한다.

## 8. 사생활 보호 문서화

README 사생활 보호 절에 예외를 명시한다 — 마이크는 응급 구간(낙상 확정~해제·신고·회복)에만
켜지고, 그동안의 오디오는 브라우저 STT를 거쳐 구글 서버로 전송된다. 평상시에는 마이크가 꺼져
있다. "영상은 기기를 벗어나지 않는다" 원칙의 유일한 예외이며, 생명이 사생활에 우선하는 순간으로
설계했다는 판단 근거를 함께 적는다.
