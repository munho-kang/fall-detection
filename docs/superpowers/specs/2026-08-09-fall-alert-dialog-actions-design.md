# 사고 발생 창 전화·119 설계 — 상세 화면과 같은 두 버튼을 창에도

2026-08-09. 사고 발생 창(`fall_alert_dialog.dart`)에 알림 상세 화면(`fall_detail.dart`)과 같은
"돌봄 대상자에게 전화"·"119 긴급 신고" 버튼을 넣는다.
브레인스토밍 결정 기록이며 구현 계획의 입력이 된다.

## 1. 범위와 결정

포함한다.

1. **사고 발생 창** — 전화·119 버튼 추가. 스타일·활성 조건은 상세 화면을 미러링한다.
2. **`lib/dial.dart` 신설** — 두 화면이 복붙하던 발신 로직과 119 번호 상수를 공용화한다.
3. **상세 화면 정리** — 자체 `_dial`·`_emergencyPhone`을 지우고 공용 헬퍼를 쓴다. 동작 불변.

범위 밖.

- **창 안에서의 알림 확인·기록 삭제** — 요청에 없다. 확인 버튼과 상세 화면이 이미 맡고 있다.
- **창의 주기 재조회** — 상세 화면은 119 자동 신고가 도착하면 잠기도록 5초마다 다시 읽지만,
  이 창은 잠깐 떠 있는 모달이라 열릴 때의 스냅샷이면 충분하다.

### 결정 1 — 전화를 걸어도 창은 유지된다

이 창은 PopScope + `barrierDismissible: false`로 "확인 버튼이 유일한 출구"라는 계약을 갖고 있다.
전화·119 버튼은 전화 앱만 열고 창은 그대로 둔다. 통화 후 앱에 돌아와도 사고 정보가 계속 보이고,
대기열(`main_shell.dart`의 `_alertQueue`)의 다음 사고 창도 확인을 눌러야만 순서대로 뜬다.
기존 계약과 테스트("확인을 누르면 닫힌다" 등)가 그대로 유효하다.

### 결정 2 — 번호는 창이 Api로 직접 조회한다

상세 화면과 같은 패턴이다. 창에 `Api`를 넘기고 열릴 때 `getProfile()`을 한 번 불러
`elderPhone`을 얻는다(실패 시 빈 값 = 버튼 비활성). StatelessWidget은 StatefulWidget이 된다.

MainShell이 프로필을 미리 들고 문자열만 넘기는 안을 검토했으나 택하지 않았다 —
MainShell에 프로필 로드·갱신 책임이 생기고, 프로필 탭에서 번호를 바꾼 뒤 창이 낡은 번호로
전화를 걸 수 있다. 열릴 때 조회하면 항상 최신이고 코드 패턴도 상세 화면과 하나로 유지된다.

### 결정 3 — 발신 로직과 119 번호를 `lib/dial.dart`로 공용화

지금 119 번호(`01000000119`, 시연용 상수)와 `launchUrl(tel:)` + 실패 스낵바 로직은
상세 화면의 private 멤버다. 창에 복사하면 번호가 두 파일에 살게 되고, 실제 번호(`119`)로
바꾸는 날 한 곳만 고치는 사고가 가능해진다. 상수 하나와 함수 하나짜리 파일로 빼서 둘이 같이 쓴다.

이때 `launchUrl`이 던지는 예외(웹·일부 기기의 PlatformException 등)도 잡아서 같은 스낵바
("전화 앱을 열 수 없습니다.")로 흡수한다. 지금 상세 화면은 `launchUrl`이 false를 돌려주는
경우만 처리하고 예외는 그대로 터진다 — 공용화하면서 이 구멍도 메운다. UX는 동일하다.

## 2. UI — 창의 버튼 (위→아래)

```
⚠ 사고 발생
방 이름   안방
방 번호   2번
발생 시각 7월 28일 04:35

[ 📞 돌봄 대상자에게 전화 ]   ← 외곽선, surfaceContainer 배경
  (미등록 시: 프로필에서 전화번호를 등록하면 켜집니다.)
[ ⚠ 119 긴급 신고 ]          ← error 배경 채움 버튼
  (신고됨 시: 응답이 없어 119에 자동 신고되었습니다)
[ 확인 ]                      ← 기존 primary 채움 버튼, 유일한 출구
```

- **돌봄 대상자에게 전화** — `elderPhone`이 비어 있으면 비활성이고 아래에 안내문이 붙는다.
  문구·스타일 모두 상세 화면과 같다.
- **119 긴급 신고** — `event.isReported119`면 비활성이고 자동 신고 문구가 붙는다.
- **확인** — 그대로 맨 아래. 위치·스타일 불변.
- 버튼 수치(높이 48·라운드 16·아이콘 20·글자 17/w700)는 상세 화면 `_actionButton`을 따른다.
- `AlertDialog.actions`의 가로 OverflowBar 배치에 기대지 않고 Column 하나로 세로 스택한다 —
  버튼 사이 간격을 직접 제어하고 안내문을 버튼 바로 아래 붙이기 위해서다.

## 3. 엣지 케이스

- **이미 신고된 이벤트가 창에 뜰 수 있다.** 폴러(`poller.dart`)는 마지막으로 본 id보다 큰
  이벤트를 fresh로 준다. 앱이 오프라인이었다 재연결되면, 그 사이 발생해 이미 119 자동 신고까지
  끝난 이벤트가 fresh로 도착해 창에 뜬다. 이때 119 버튼은 잠기고 자동 신고 문구가 보인다 —
  상세 화면과 같은 상태가 된다.
- **프로필 조회 실패** — 빈 값 취급으로 전화 버튼 비활성 + 안내문. 상세 화면과 같다.
- **전화 앱을 못 여는 환경**(에뮬레이터·웹 일부) — 스낵바로 알리고 창은 유지된다.

## 4. 다른 부분에 미치는 영향

- **`main_shell.dart`** — 호출부가 `FallAlertDialog(api: widget.api, event: event)`가 된다.
- **`fall_detail.dart`** — `_dial`·`_emergencyPhone` 삭제, 공용 헬퍼 사용. 화면 동작 불변.
- **감지 페이지·백엔드·웹** — 손대지 않는다. 창은 이미 받은 이벤트와 프로필만 쓴다.

## 5. 테스트

**`fall_alert_dialog_test.dart`** — 창이 이제 Api를 받으므로 기존 5개 테스트에
`_FakeApi extends Api`(`getProfile` 오버라이드)를 주입한다. 신규는:

1. 번호가 등록돼 있으면 전화 버튼이 활성이다.
2. 번호가 없으면 전화 버튼이 비활성이고 "프로필에서 전화번호를 등록하면 켜집니다."가 보인다.
3. 신고 전 이벤트는 119 버튼이 활성이고 자동 신고 문구가 없다.
4. 신고된 이벤트는 119 버튼이 잠기고 "응답이 없어 119에 자동 신고되었습니다"가 보인다.
5. 전화·119 버튼을 눌러도 창이 유지된다(확인만이 출구). 테스트는 `UrlLauncherPlatform.instance`를
   실패 페이크로 교체해 스낵바 경로를 함께 지나간다 — Windows 호스트의 `flutter test`는
   Dart 플러그인 레지스트런트로 진짜 런처를 등록할 수 있어(호스트에서 전화 앱이 열린다)
   페이크 교체가 필수다.

**`main_shell_alert_test.dart`** — 셸이 띄우는 창이 `getProfile()`을 부르게 되므로
`_FakeApi`에 `getProfile` 오버라이드를 더한다(테스트 프레임워크의 HTTP 400 스텁에 기대지 않는다).

**`fall_detail_test.dart`** — 수정 없음. 공용화는 동작 불변이라 기존 테스트가 그대로 회귀를 막는다.

**회귀 전체** — `flutter analyze` · `flutter test`.
