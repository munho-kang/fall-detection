# 낙상 기록 삭제 설계 — 확인한 기록만, 웹·앱 양쪽에서

2026-07-27. 보호자가 이미 확인한 낙상 기록을 목록에서 지울 수 있게 한다.
브레인스토밍 결정 기록이며 구현 계획의 입력이 된다.

## 1. 범위와 결정

포함한다.

1. **서버** — `DELETE /api/falls/{id}/` 엔드포인트 하나. 웹과 앱이 같이 쓴다.
2. **보호자 페이지(web)** — 확인한 기록에 "삭제" 버튼.
3. **앱(Flutter/iOS)** — 낙상 상세 화면에 "기록 삭제" 버튼.

범위 밖.

- **전체 삭제 / 일괄 삭제** — 요청에 없다.
- **휴지통·복구** — 완전 삭제를 택했으므로 되돌리는 경로를 만들지 않는다.
- **역할(role) 체계** — 이 프로젝트에 역할 개념이 없다. `Guardian`이 유일한 사용자 엔티티이고
  토큰이 곧 보호자 신원이다. "보호자로 로그인 된다면"은 로그인된 상태를 뜻하며,
  서버가 이미 하는 소유권 필터(`findByIdAndGuardianId`)가 그대로 권한 검사가 된다.

### 결정 1 — 소프트 삭제가 아니라 완전 삭제

DB 행을 지운다. `deleted_at` 컬럼과 조회 필터를 더하는 소프트 삭제를 검토했으나 택하지 않았다.

- 방 삭제(`RoomService.delete`)가 이미 완전 삭제다. 같은 프로젝트 안에서 삭제의 의미가 갈리면 안 된다.
- "영상도 좌표도 남기지 않는다"는 이 프로젝트의 사생활 보호 기조와 맞는다. 지우라면 지운다.
- Flyway 마이그레이션과 전 조회 경로의 필터가 필요 없어진다.

대가는 되돌릴 수 없다는 것이다. 그래서 양쪽 UI 모두 확인 단계를 거친다(결정 3).

### 결정 2 — 미확인 기록은 서버가 막는다

"보호자가 확인하지 않은 낙상은 사라지지 않는다"는 안전 규칙이다.
UI에서 버튼만 숨기면 규칙이 아니라 장식이 된다. 서버가 400으로 거절해야 규칙이 된다.
비용은 `if` 한 줄과 테스트 하나다.

### 결정 3 — 삭제 전 확인 단계

되돌릴 수 없으므로 양쪽 다 확인을 받는다. 웹은 방 삭제와 같은 `confirm()`,
앱은 `showDialog`를 쓴다.

## 2. API

기존 엔드포인트는 그대로다. 추가분만 적는다.

```
DELETE /api/falls/{id}/
  204 No Content              확인한 내 기록 — 행 삭제, 본문 없음
  404 {"detail": "찾을 수 없습니다."}
                              없는 id 또는 남의 기록 (존재 자체를 드러내지 않는다)
  400 {"non_field_errors": ["확인하지 않은 낙상은 삭제할 수 없습니다."]}
                              acknowledged_at 이 null
  401                         토큰 없음/무효 (기존 필터가 처리)
```

- 상태 코드와 끝 슬래시는 `DELETE /api/rooms/{id}/`와 같은 모양이다.
- 404 판정은 `acknowledge`와 동일하게 `FallEventRepository.findByIdAndGuardianId`로 한다.
  guardian 조건을 건 조회라 남의 기록은 401도 403도 아닌 404가 된다 — 존재 여부가 새지 않는다.
- 400은 `FieldValidationException`으로 던진다. `GlobalExceptionHandler`가 DRF 호환 JSON으로
  바꾸므로 웹의 `firstErrorMessage()`와 앱의 `_firstErrorMessage()`가 그대로 문구를 꺼낸다.
- 메시지는 `FallService`의 상수로 두고 테스트가 그 상수를 참조한다
  (`RoomService.DUPLICATE_ROOM_MESSAGE`와 같은 방식).

**404와 400의 순서.** 소유권 조회를 먼저 하고, 그 다음 확인 여부를 본다.
남의 미확인 기록에 DELETE를 보내면 400이 아니라 404다 — 400을 먼저 주면 "그 id는 존재하며
아직 미확인"이라는 정보가 새기 때문이다.

리포지토리 변경은 없다. `findByIdAndGuardianId`가 이미 있다.

## 3. 보호자 페이지 (web)

`web/js/guardian.js`의 `refreshFalls()` 안에서 버튼 분기를 갈래로 바꾼다.
지금은 미확인일 때만 "확인" 버튼이 붙는데, 확인한 기록에는 "삭제"가 붙는다.
한 항목에 버튼은 항상 하나다.

```
안방 1 · 7월 26일 14:30 · 미확인   [확인]
안방 1 · 7월 26일 09:12 · 확인함   [삭제]
```

- 누르면 `confirm("7월 26일 09:12 안방 1 낙상 기록을 삭제할까요?")`.
- 성공하면 `refreshFalls()`로 다시 그린다. 실패하면 기존 `showError`로 문구를 띄운다.
- `web/js/api.js`에 `deleteFall(id)`를 더한다. `deleteRoomById`와 같은 모양이되,
  400의 서버 문구를 살리기 위해 `firstErrorMessage`를 쓴다.

**5초 폴링과의 충돌은 없다.** 목록은 원래 폴링이 통째로 다시 그린다.
삭제 직후의 `refreshFalls()`가 폴링과 겹쳐도 둘 다 서버 상태를 그대로 그리므로 결과가 같다.
새로 관리할 클라이언트 상태가 없다. 이미 지워진 id에 DELETE가 한 번 더 가면 404로 끝나 무해하다.

## 4. 앱 (Flutter/iOS)

### 삭제 버튼은 상세 화면에 둔다

`app/lib/screens/fall_detail.dart`의 "확인함으로 표시" 아래에 "기록 삭제"를 넣는다.
목록 스와이프 삭제(`Dismissible`)를 검토했으나 택하지 않았다 — 목록은 5초 폴링이 `_events`를
통째로 갈아치우는 자리라, 스와이프 애니메이션 도중 리스트가 교체되면 상태가 꼬인다.
상세 화면은 폴링 대상이 아니어서 이 문제가 없고, 웹의 "확인 → 삭제" 순서와도 같아진다.

- 미확인이면 버튼이 비활성이고 라벨이 "확인한 뒤 삭제할 수 있습니다"가 된다.
  서버가 400으로 막는 규칙을 화면이 미리 설명한다.
- 누르면 `showDialog` 확인창을 거친다.
- 실패하면 기존 `_acknowledge`와 같이 SnackBar로 서버 문구를 띄운다.
- 위험한 동작이므로 `OutlinedButton.icon`에 `colorScheme.error`를 쓴다.

### 삭제 후 목록 반영 — pop 결과의 null 경로

지금 상세 화면은 `pop(_event)`로 갱신된 이벤트를 돌려주고, 목록이 `indexWhere`로 그 자리만
교체한다(`fall_list.dart:154`). 삭제는 "그 항목이 사라졌다"를 알려야 하는데,
결과 타입을 sealed 클래스로 늘리는 대신 null 경로에 `_refresh()`를 붙여 끝낸다.

```dart
final updated = await Navigator.of(context).push<FallEvent>(...);
if (updated != null) {
  // 기존 — 확인 상태만 그 자리에서 교체
} else {
  await _refresh();   // 삭제 또는 스와이프 백 — 서버 상태로 다시 그린다
}
```

삭제는 `pop(null)`이므로 목록이 서버에서 다시 받아 그린다.
스와이프 백도 같은 경로를 타는데, `fall_detail.dart:81` 주석이 지금
"스와이프 백으로 나가면 null이 되지만 5초 폴링이 곧 새로 고친다"고 아쉬움을 인정하고 있다.
이 변경이 그것도 같이 해소한다. 새 타입도 콜백도 없이 세 줄이다.

### API 클라이언트

`app/lib/api.dart`에 `deleteFall(int id)`를 더한다. `deleteRoom`과 같은 모양이되,
400일 때 `_firstErrorMessage`를 써서 서버의 한국어 문구가 그대로 SnackBar에 뜨게 한다.

## 5. 다른 부분에 미치는 영향

**앱 알림은 다시 뜨지 않는다.** `poller.dart`의 `NewEventTracker`는 응답의 최대 id만 기억한다.
기록이 지워져 최대 id가 낮아져도, 새로 생기는 이벤트의 id는 언제나 그보다 크다.
따라서 이미 알린 낙상이 삭제 때문에 다시 알림으로 뜨는 경우는 없다.

**감지 페이지는 손대지 않는다.** 삭제는 보호자 쪽 동작이고 감지 파이프라인과 무관하다.

## 6. 알려진 한계 — 삭제한 기록이 되살아나는 희박한 경우

감지 페이지의 오프라인 큐가 같은 낙상을 재전송하면, 서버의 중복 조회
(`guardian, room_name, room_number, occurred_at`)가 실패해 새 행으로 살아난다.
다만 큐에 들어가려면 POST가 3회 실패해야 하고, 그러면 애초에 서버에 행이 없어 삭제할 것도 없다.
"행은 저장됐는데 응답만 유실된" 경우에만 성립한다.

대응하지 않는다. 막으려면 삭제한 (guardian, room, number, occurred_at) 조합의 묘비를 남겨야 하는데,
완전 삭제를 택한 이유와 정면으로 어긋난다. 이 문서에 기록으로 남기는 것으로 갈음한다.

## 7. 테스트

**백엔드** — `FallApiTest`에 3개를 더한다. 웹과 앱이 같은 엔드포인트를 쓰므로 계약 검증은 여기 한 곳이면 된다.

1. 확인한 기록 DELETE → 204이고, 이후 `GET /api/falls/`에서 사라진다.
2. 미확인 기록 DELETE → 400이고 본문이 `FallService`의 상수 문구다. 행은 남아 있다.
3. 남의 기록 DELETE → 404. 남의 미확인 기록도 400이 아니라 404다(정보 유출 방지).

**앱** — `app/test/`에는 `poller_test.dart` 하나뿐이고 순수 로직만 다루는 관례다.
삭제는 위젯·네트워크 경로라 여기에 맞지 않는다. 대신 `flutter analyze`와 `flutter test`로 회귀만 막는다.

**웹** — `web/tests/`도 순수 로직(`detector`·`queue`·`pollBanner`)만 다루고 `guardian.js`는 테스트가 없다.
관례를 따라 DOM 테스트를 새로 만들지 않는다.

**수동 검증** — `docs/manual-verification.md`에 절차를 넣는다. 웹과 앱 각각에서
(a) 미확인 기록에 삭제 버튼이 없거나 비활성인지, (b) 확인 후 삭제하면 목록에서 사라지는지,
(c) 같은 계정의 다른 화면(웹↔앱)에서도 5초 안에 사라지는지.

**회귀 전체** — `./gradlew test`(backend), `npm test`(web), `flutter analyze`·`flutter test`(app).
