# 창업 캠프 발표 피칭덱 설계 (2026-07-27)

2026 제주 지역대학 연합 창업 캠프 발표용 피칭덱. 사전과제(문제 정의서·MVP 개발 계획서)와
기존 과제 발표자료 `web/pre.html`을 잇는 세 번째 산출물로, 심사 관점(문제→시장→기술→기능→사업)에
맞춰 재구성한다. 사용자 요청 — 문제정의·시장조사 결과·AI 활용 방식(MediaPipe)·핵심 기능 포함,
웹검색 근거와 캡쳐 이미지 포함.

## 접근 비교

- **A. `pre.html`을 확장** — 기각. pre.html은 "과제 프로젝트 발표"(기술 서사)로 완결돼 있고,
  창업 피칭은 시장·경쟁·BM이 축이라 한 파일에 섞으면 두 서사가 모두 흐려진다. 기존 산출물 보존 원칙과도 어긋난다.
- **B. 새 파일 `web/pitch.html` + pre.html 디자인 시스템 계승** — 채택. 같은 토큰(다크, #3987e5 액센트,
  카드·타일·기사캡쳐 컴포넌트)과 내비게이션 JS를 이어받아 팀 자료의 시각 일관성을 유지하면서 서사만 갈아끼운다.
  임베드된 기사 캡쳐 7장을 재사용할 수 있다.
- **C. PPT/Word(IR Deck.docx)** — 기각. IR Deck.docx는 빈 문서였고, 저장소의 차트·캡쳐·검증 흐름과 단절된다.

## 데이터·출처 원칙

- 외부 수치는 이번 웹 리서치(통계·시장·기술 3에이전트)에서 **출처 페이지를 실제로 확인한 값만** 쓴다.
  사전과제 수치와 다르면 검증치를 우선하고 차이를 context-notes에 기록한다.
- 제품 수치(테스트 개수·실측 결과·임계값)는 README·checklist 현재값을 쓴다 — 사전과제의 "테스트 21개"는
  이미 84개+E2E 12개로 늘었다.
- 119 자동 신고는 실발신이 아니라 기록임(README "알려진 한계")을 덱에서도 정직하게 각주로 표기한다.
  심사 질의에서 뒤집히는 과장을 만들지 않는다.
- 마지막 장에 전체 출처를 나열하고, 기사 캡쳐에는 인용 목적·저작권 고지를 유지한다.

## 디자인·차트 규칙

- pre.html 토큰 계승(다크 단일 테마 — 발표장 전제). 슬라이드 16:9 뷰포트 고정, ←/→·F 내비게이션,
  `@media print` 페이지 나눔(PDF 제출 대응)까지 동일 패턴.
- 차트는 정적 SVG figure(발표·인쇄 맥락이라 호버 생략). dataviz 원칙 준수 — 축 1개, 시리즈 색 고정,
  텍스트는 잉크 토큰, 상태색(critical 등)은 의미에만. 사용할 색 조합은 `validate_palette.js`를 다크 서피스로 실행해 검증.
- 대용량 base64 캡쳐 때문에 Write로 직접 조립하지 않고, 플레이스홀더 템플릿 + 파이썬 치환 스크립트(스크래치패드)로
  `web/pitch.html`을 생성한다.

## 검증 계획

1. 파이썬 `html.parser`로 태그 정합성 검사, `node --check`로 내비게이션 JS 구문 검사.
2. 이미지 데이터 URI 디코드 가능 여부 확인. 팔레트 검증 스크립트 통과.
3. `cd web && npm test` 회귀(덱은 정적 파일이지만 web/ 안 변경이므로 확인).
4. 로컬 서버로 열어 슬라이드 이동·페이지 수 확인.

## 자율 진행 가정 (사용자 부재 중 결정)

- 산출물 파일명 `web/pitch.html`, 커밋 포함. IR Deck.docx는 비어 있어 참고 대상에서 제외.
- 팀원 표기는 사전과제 역할란의 "박혜영"을 따른다(팀원명란 "박혜여"와 불일치 — 확인 필요).
- 발표 시간 안내가 없어 16장(5~7분 발표 분량)으로 잡는다.
- Artifact 발행은 하지 않는다 — 팀은 이 Mac에서 로컬 파일로 발표하는 흐름(pre.html과 동일)이다.
